## 1. 审计结论

**当前版本不满足作为真实数据保险库发布的条件。** 主要问题发生在密钥来源、身份权限、备份恢复链路和持久化保证上，不能仅通过增加按钮禁用或调整界面文案解决。

四项发布阻断问题已经用虚构数据复现：

1. `.legacylock` 导出包不需要密码、Secret Key 或任何 U 盘，即可利用包内公开信息解密。
2. 本地密库的解密材料全部来自同机保存的配置，读取这些文件即可解密，无需知道用户密码。
3. 原电脑锁屏的“双 U 盘解锁”按钮只检查文件存在等状态，没有验证两把私钥，也没有执行解密。
4. Rust 密库只需任一方私钥和密包内另一方公钥即可解密，不是“两份秘密缺一不可”的 2-of-2 恢复机制。

另外，继承只读权限可以在退出或重启过程中丢失；前端写入的密库与 Rust 解锁算法不兼容；介质迁移只显示进度而没有复制文件；写入失败可能仍然提示成功。上述问题直接影响你要求的“原电脑只读继承”和“新电脑导入后未经双凭据不得修改”。

本次未修改业务源码，只新增审计材料、复现脚本和截图。**复现脚本中的 PASS 表示成功复现问题，不代表安全检查通过。**

## 3. 需求与文档基线

以你本次说明作为最高优先级：所有者可以维护密库和设置应用；继承者用主、副 U 盘访问原电脑或在其他电脑恢复后，默认只能查看；获得所有者密码和密钥后才可修改数据或安全设置。

建议把要求固化为以下矩阵，避免“能解密”自动等于“能修改”：

| 场景 | 读取 | 修改数据 | 更改安全设置 | 持久化方式 |
| --- | --- | --- | --- | --- |
| 所有者通过已定义的本机认证解锁 | 允许 | 允许 | 敏感操作重新认证 | 原保险库，事务提交 |
| 双 U 盘在原电脑恢复 | 允许 | 拒绝 | 拒绝 | 不自动改写原保险库 |
| 双 U 盘在新电脑恢复 | 允许 | 拒绝 | 拒绝 | 临时读取或保留身份的只读缓存 |
| 密码＋Secret Key 验证并取得原库管理能力 | 允许 | 允许 | 允许 | 明确取得管理权限后保存 |
| 未认证／锁屏 | 拒绝 | 拒绝 | 拒绝 | 不解密、不写入、不销毁 |
| 新电脑创建了一个新账户／新密码 | 只对其新库有效 | 不应取得导入原库的管理能力 | 不应改变原库身份 | 原库与新库分开 |

语言与临时缩放是否对继承者开放，可以作为阅读辅助单独定义；本报告不把它们与更改密码、换盘、销毁等安全管理操作混为一类。默认不让继承者持久化修改原库配置。

另一个必要边界：继承者既然被允许读取明文，就能在其他软件中复制、修改自己的副本。可实现的安全目标是**不能产生能通过原所有者签名验证的修改版本**，而不是保证对方的操作系统绝对无法修改任何文件。

## 4. 详细发现

优先级定义：P0 为发布阻断；P1 为正式保存真实重要数据前必须修复；P2 为应纳入下一轮稳定性和可用性整改的问题。级别按本产品用途和实际影响判断，不使用虚假的精确 CVSS 分数。

### P0-01 导出包存在不需要秘密的解密通道

**证据：** [exportEncryptedVaultPackage](C:/XMWJJ/xr-LegacyLock/src/services/cryptoService.ts:614)、[importEncryptedVaultPackage](C:/XMWJJ/xr-LegacyLock/src/services/cryptoService.ts:742)。复现 A01。

导出时除了密码＋Secret Key 通道，还始终生成双盘密文副本。其种子是 `DUAL_USB_READONLY_SECRET:<userPublicHex>:<heirPublicHex>`。两段公钥直接保存在导出文件中；未配置时又使用源码中的固定默认字符串。盐、IV、密文也都在同一文件中。

因此获得一个导出包的人即可恢复所有资产，不必破解密码、不必读 U 盘。`isReadOnly` 只是返回值标志，不会限制攻击者使用解密后的数据。载荷还包含整个 plan，可能进一步暴露其中保存的 Secret Key。

**修复：** 删除由公开数据或常量派生的秘密通道；恢复槽必须由真正的两份独立秘密解封装随机数据密钥。所有者凭据／签名私钥不得作为普通继承可读数据一并打包。对已有格式制定受控迁移，不能只修新导出而宣称历史包安全。

**验收：** 单独持有新导出包、包头、公钥、完整源码和任意一个盘都不能解密；只有预定的完整凭据组合成功。

### P0-02 本地“加密存储”的密钥材料与密文共同保存

**证据：** [getLocalEncryptionSeed](C:/XMWJJ/xr-LegacyLock/src/services/cryptoService.ts:1014)、[saveSecureLocalItems](C:/XMWJJ/xr-LegacyLock/src/services/cryptoService.ts:1095)、[启动加载](C:/XMWJJ/xr-LegacyLock/src/App.tsx:346)。复现 A02、A03。

本地种子由 localStorage 中的 masterPasswordHash、secretKeyHash、userPublicHex 拼接；无主密码时使用固定常量。这些已存哈希在这里相当于可直接使用的解密秘密，而不是仅供密码验证的值。启动时 `loadSecureLocalItems()` 在锁屏验证之前直接加载明文资产。

此外，保存过程外层捕获异常后会把资产直接写入 `legacylock_items` 明文条目。本次注入随机源失败，确认触发该分支。首次设置还将原始 Secret Key 存入 plan 并持久化：[初始化凭据](C:/XMWJJ/xr-LegacyLock/src/App.tsx:576)。

**影响：** 能读取应用数据目录的人无需用户密码即可取得资产；锁屏只是视图遮挡；异常路径会进一步降级成明文存储。

**修复：** 使用随机 VMK，凭输入密码／密钥派生 KEK 来解封装 VMK；认证前不加载资产明文；可选的系统凭据存储需另有明确威胁模型。加密或存储失败必须返回失败，绝不退回明文。不要将原始 Secret Key 与密文并存。

### P0-03 原电脑双盘解锁只验证存在性，没有验证密钥

**证据：** [驱动器筛选](C:/XMWJJ/xr-LegacyLock/src/components/LockScreen.tsx:118)、[双盘按钮](C:/XMWJJ/xr-LegacyLock/src/components/LockScreen.tsx:559)、[Windows 文件探查](C:/XMWJJ/xr-LegacyLock/electron/main.cjs:516)、[解锁回调](C:/XMWJJ/xr-LegacyLock/src/App.tsx:825)。复现 A07、A12。

按钮用 `hasUserKey` 和 `hasHeirKey` 判定就绪；扫描器用 `existsSync` 判定文件存在；点击时只校验副盘绑定，再直接调用回调展示已经加载的本地数据。未读取和验证私钥，没有把密钥与当前 Vault ID 绑定，没有调用 Rust 解锁器。

空文件也能满足存在性条件。副盘绑定文件不存在会放行。同一个驱动器若同时含两种文件，也可被两个 `find` 同时选中；没有不同物理设备的校验。

**影响：** 能在当前电脑会话或锁屏前操作介质的人，可以用伪造存在性状态绕过继承认证读取本地数据；并不需要获得真实双盘秘密。

**修复：** 按当前保险库验证两份恢复材料并真实解封装，成功后才加载明文和签发只读会话。设备发现不能承担认证职责。锁屏前后必须清理敏感工作区。

### P0-04 Rust 的 X25519 协商不是 2-of-2 秘密恢复

**证据：** [密钥派生与加密](C:/XMWJJ/xr-LegacyLock/crypt/src/crypto.rs:129)、[容器公开双方公钥](C:/XMWJJ/xr-LegacyLock/crypt/src/crypto.rs:162)、[解锁检查](C:/XMWJJ/xr-LegacyLock/crypt/src/crypto.rs:179)。复现 R01。

Rust 密钥为 `SHA256(X25519(user_private, heir_public))`，也等于 `SHA256(X25519(heir_private, user_public))`。容器公开双方公钥，所以**副盘私钥＋密包**已经足够；主盘同理。CLI 强制要求两个文件参数，无法改变密码学性质。

本次先用当前 Rust CLI 生成钥匙和密库，再只向独立解密操作提供副盘私钥与密包内主盘公钥，成功恢复虚构资产。[RFC 7748](https://www.rfc-editor.org/rfc/rfc7748#section-6.1) 描述的正是各方用自己的私钥和对方公钥计算共享秘密的协议。

**修复：** 重新设计恢复 key slot，用经审查的两份秘密组合方案保护 VMK；所有者日常槽与继承槽分离。普通 U 盘上的秘密文件可被复制，产品不能把“双份秘密”宣传成永远不可复制的实体硬件存在证明。

### P1-01 继承只读身份不能跨退出／重启保持，提权未始终验证原库双凭据

**证据：** [默认角色](C:/XMWJJ/xr-LegacyLock/src/App.tsx:214)、[导入回调](C:/XMWJJ/xr-LegacyLock/src/App.tsx:675)、[退出恢复](C:/XMWJJ/xr-LegacyLock/src/App.tsx:748)、[提权校验](C:/XMWJJ/xr-LegacyLock/src/services/cryptoService.ts:143)、[导入处理](C:/XMWJJ/xr-LegacyLock/src/components/ImportExportView.tsx:262)。复现 A04、A08、A11。

只读标志只在 React 内存里；导入数据进入 items 后，自动保存逻辑仍然写本机。重启时默认 `OWNER`、`heirCanModify=true`。新安装如果没有本机密码配置，会直接可编辑；有本机配置时，验证的是该电脑配置，不一定是原保险库所有者的配置。

“退出接管”还会先恢复 OWNER 和修改权限，然后仅靠锁屏挡住界面；该锁屏允许主密码或 Secret Key 任意一个解锁，无主密码时直接恢复。这不满足继承者必须输入两项凭据才能提权的要求。

普通导入丢弃返回的 plan 和 isReadOnly。底层 `verifyTakeoverCredentials` 在配置缺少相应因子标志时跳过检查，配置对象存在但两项都关闭也返回成功。UI 对密码非空的检查不能补足原库身份验证。

**修复：** 管理权必须从原库 owner key slot 及签名私钥的解封装结果获得。引入统一状态机；退出和重启回到 LOCKED，不能预先设置 OWNER。只读会话不能自动改写原库，保存副本时保留库身份与权限语义。

### P1-02 Ed25519、防回滚与六项自检并未真正实现

**证据：** [模拟签名](C:/XMWJJ/xr-LegacyLock/src/services/cryptoService.ts:280)、[自检](C:/XMWJJ/xr-LegacyLock/src/services/cryptoService.ts:341)。复现 A05。

所谓 owner_signature 是公开哈希加公钥再 SHA-256，不是 Ed25519 签名；自检只看长度为 64。对象检查只看 items 非空和 ciphertext 非空；公钥检查只看非空；离线救援存在性默认 true；防回滚只判断序号至少为 1。

本次以无效密文、`x/y` 公钥、64 个 `z` 的伪签名构造容器，六项全部通过并得到 Healthy／100。常规自动写入不推进 sequence；缺少 serverHash 时每次加密生成新的 Vault ID。不存在可信的所有者签发和历史连续性。

**修复：** 实现真正的所有者签名与可信公钥身份绑定，读取时验签及校验对象，签名覆盖格式、权限和关键元数据。防回滚需定义可信的已见最大版本；在全新离线电脑上没有外部可信锚点时，不应宣称能识别所有旧快照。未执行的检查显示“未验证”，不能默认绿色。

### P1-03 密钥制作与恢复没有形成完整产品流程，读写算法互不兼容

**证据：** [U 盘配置保存](C:/XMWJJ/xr-LegacyLock/src/components/UsbPasswordModal.tsx:93)、[本地配置更新](C:/XMWJJ/xr-LegacyLock/src/App.tsx:499)、[双盘导入](C:/XMWJJ/xr-LegacyLock/src/services/cryptoService.ts:1267)、[主进程解锁](C:/XMWJJ/xr-LegacyLock/electron/main.cjs:1034)。复现 A06、R04，并核对知识图谱调用关系。

U 盘密码弹窗仅更新本机密码哈希和绑定文件，没有制作真实 `user-key.bin`、`heir-key.bin`、`config.bin` 的完整流程。`generateKeys`、`encryptVault` 桥接接口没有发现生产 UI 调用者。`generateDualUsbKeyBlobs` 是 SHA-256 模拟公钥，也不能当作 Rust X25519 密钥使用。

App 自动写库用 `encryptVaultWeb` 的公开元数据／哈希种子，双盘恢复却交给 Rust 的 DH 密钥解密。本次使用真实 Rust 公钥和同一组密钥验证，前端写出的密文无法被 Rust 解锁。

双盘导入未传 vaultPath，主进程默认读取当前电脑 userData／项目下的 vault.locked，并不会自动选中 U 盘里的密库。没有找到本机数据时，新电脑不能据此完成用户期望的恢复。浏览器降级路径还会把 currentItems 直接作为“解密成功”返回。

**修复：** 先完成“全新安装→初始化→制作两盘→写入测试数据→另一台干净电脑只读恢复”的单一路径。统一格式和解封装核心；浏览器能力不足时明确禁用硬件功能，不能返回模拟成功。

### P1-04 介质迁移显示成功，但没有迁移任何文件

**证据：** [handleStartMigration](C:/XMWJJ/xr-LegacyLock/src/components/MediaMigrationModal.tsx:52)。复现 A10。

函数仅两次 setTimeout 后调用成功回调，没有源介质读取、目标写入、哈希比对、可恢复性验证或错误处理。用户据此停用旧盘会失去唯一副本。

### P1-05 保存目标和成功提示不可信

**证据：** [handleSaveToDrive](C:/XMWJJ/xr-LegacyLock/src/App.tsx:650)、[导出写入](C:/XMWJJ/xr-LegacyLock/src/components/ImportExportView.tsx:213)、[save-container IPC](C:/XMWJJ/xr-LegacyLock/electron/main.cjs:1100)。复现 A09。

### P1-06 自动保存、改密码和读失败缺少事务保证

**证据：** [自动回写](C:/XMWJJ/xr-LegacyLock/src/App.tsx:419)、[IndexedDB 写入](C:/XMWJJ/xr-LegacyLock/src/services/cryptoService.ts:988)、[保存与加载](C:/XMWJJ/xr-LegacyLock/src/services/cryptoService.ts:1095)、[改密码配置](C:/XMWJJ/xr-LegacyLock/src/App.tsx:611)。静态确认的故障路径，未做真机断电实验。

多次异步加密／保存没有全局写队列和修订检查；500 ms 防抖不能取消已经开始的旧任务。旧任务可能晚于新任务落盘。关闭应用也没有等待统一保存完成。

IndexedDB 成功按单个 put request 回调处理，没有等待 transaction.oncomplete；加密大数据时 IDB 失败，超过 3 MB 又不写 localStorage，函数仍正常返回。读取失败最终返回 null，App 将其当作空库或示例库，再自动回写，缺少保留损坏原件的恢复状态。

修改密码会先保存新哈希配置，再异步重加密，配置与密文没有共同事务。此时崩溃可能使旧数据与新派生种子不匹配。文件容器使用直接 writeFileSync 覆盖，没有临时文件、fsync、原子替换和备份版本。

**修复：** 引入串行事务提交、持久化 revision、旧版本备份及恢复日志；密码轮换只原子替换包裹 VMK 的槽。区分不存在、损坏、认证失败、I/O 失败，后几种状态禁止自动写空库。加入磁盘满、权限错误、进程退出和断电故障注入。

### P1-09 Electron 特权边界偏弱，运行时存在依赖风险

**证据：** [BrowserWindow 设置](C:/XMWJJ/xr-LegacyLock/electron/main.cjs:388)、[IPC 处理](C:/XMWJJ/xr-LegacyLock/electron/main.cjs:849)、[端口复用](C:/XMWJJ/xr-LegacyLock/electron/main.cjs:337)、[CSP](C:/XMWJJ/xr-LegacyLock/index.html:6)。复现 A13 仅为直接 IPC 单元调用。

**修复：** 升级到受支持且经兼容验证的 Electron；启用 sandbox；统一验证 sender、capability、路径和参数；只加载受信任本地资源，不复用未知服务。按 [Electron 官方安全指南](https://www.electronjs.org/docs/latest/tutorial/security) 核对 IPC、导航和新窗口限制。

## 5. 建议的产品流程与修改顺序

### 第一批：恢复可信的安全边界

1. 暂停把当前版本称为“审计通过／零漏洞”，撤下模拟迁移和虚假自检结论。
2. 为密码、Secret Key、双盘秘密、VMK、Owner 签名私钥定义数据流和存储位置。
3. 统一格式及密码核心；修复四项 P0，建立真正的所有者槽和双秘密只读恢复槽。
4. 权限从已解封装的能力产生，在主进程／核心执行；锁屏、退出、重启不得恢复默认写权限。
5. 禁止加密失败写明文，禁止错误恢复为空库后自动覆盖。

### 第二批：证明长期可恢复和可保存

1. 实现单一写队列、原子提交、版本快照、改密码事务和失败恢复。
2. 完成真实双介质制作与回读验证，明确两盘分别保存什么。
3. 完成“原电脑不存在、没有网络、只有两盘和应用”的新电脑恢复演习。
4. 迁移先复制并验证，再切换；旧副本留存直到验收完成。
5. 每平台构建密码核心并执行安装后的离线恢复测试；提供独立只读恢复工具和格式说明。

### 第三批：重排 UI 与统一文档

推荐欢迎页直接提供三个入口：**创建新保险库、打开已有保险库、继承只读恢复**。

所有者首次使用按“设置凭据→保存并核对救援卡→录入测试资产→选择主盘和副盘→写入→回读→恢复演习”逐步完成。未完成恢复验证前，持续显示“继承配置未完成”，不显示“已激活”。

继承流程按“选择原库→识别两份恢复材料→验证库身份和完整性→只读查阅”完成，始终显示原 Vault ID、版本、备份日期、数据来源和“只读”标志。“取得管理权限”独立验证原所有者密码＋Secret Key；退出后销毁会话，不能自动切成 OWNER。

设置页建议分为“本机显示偏好”“保险库安全”“备份与介质”“危险操作”。把锁屏密码、恢复凭据、导出密码的区别写在对应操作旁，避免用户先读长篇技术文档才能判断。

## 6. 修复后的最低验收清单

| 编号 | 操作／故障 | 必须达到的结果 |
| --- | --- | --- |
| T01 | 仅密包；仅主盘；仅副盘；单盘＋密包 | 无法恢复明文 |
| T02 | 真双盘／空文件／错误密钥／同一盘两文件／不同库两盘 | 只有正确材料组合恢复指定库 |
| T03 | 原电脑双盘只读→退出→主密码单因子解锁 | 不得绕过原库双凭据提权 |
| T04 | 新电脑恢复→关闭→重启→新增／修改／设置 | 始终只读，直到原库管理认证成功 |
| T05 | 新电脑先设置自己的密码再导入他人库 | 本机新密码不能取得原库写权限 |
| T06 | 错密码、错 Secret Key、缺失安全配置、只输入其中一项 | 提权全部拒绝；损坏配置不能当未保护库 |
| T07 | 改密、保存、退出同时发生 | 至少保留一个可用完整版本，界面准确报告提交状态 |
| T08 | 写满磁盘、权限拒绝、IDB 失败、大附件 | 不丢失旧数据、不落明文、不报假成功 |
| T09 | 保存到不同阶段终止进程／断电／拔盘 | 恢复到旧完整版本或新完整版本 |
| T10 | 篡改正文、头、签名、generation、权限、期限 | 认证拒绝或准确显示未验证，不报健康 |
| T11 | 未知版本、短 Nonce、超大 iterations、非法条目类型 | 有界、清晰失败，无崩溃和破坏性回写 |
| T12 | 迁移至新盘后只使用新盘恢复 | 数据、附件、Vault ID、权限和签名保持正确 |
| T13 | 锁屏／系统休眠／系统锁定／拔掉任一恢复介质 | 按定义锁定并释放会话，不留下可继续编辑页面 |
| T14 | 5→60 或 60→5 分钟、禁用后再启用自动锁屏 | 本次会话即时采用新设置 |
| T15 | 下载救援卡→重生成密钥→继续保存 | 必须重新确认与当前密钥匹配的卡 |
| T16 | 800×500、常见 DPI、125%／200% 缩放、键盘导航 | 核心按钮可到达，锁屏背景不可交互，模态焦点正确 |
| T17 | 干净 Windows/macOS/Linux 安装／便携移动位置 | 核心存在、版本匹配、离线恢复成功 |
| T18 | 历史格式 Golden Vault 用新版及独立 Reader 打开 | 不自动破坏旧格式，完整恢复或明确说明不支持 |

## 7. 已有可保留的基础

项目已经使用真实 AES-GCM、随机 nonce、密码加盐哈希和 Rust 随机密钥生成；存在继承只读界面、部分 CRUD 防护、独立销毁确认、单实例限制和 Electron contextIsolation。前端构建与现有 Rust 测试也能运行。这些是可继续利用的基础。

但当前最优先事项是使**秘密确实保密、权限确实不可越过、备份确实能恢复、写入确实已完成**。修复完成后，应由未参与实现的人复核密码协议，并在干净电脑和真实介质上完成恢复演习，再更新手册中的能力声明。
